# 面试复盘分析工具 — 产品与技术方案

## 一、产品概述

**产品定位**：求职顾问工作台的新增工具模块，帮助老师基于学员真实面试录音、面试问答文本、JD 和简历，生成逐题面试复盘建议。

**核心价值**：输入面试材料 → 自动转写/整理 → AI 逐题诊断 → 输出【问题分析】+【优化建议】+【参考话术】+【知识补充】。

**使用者**：老师/顾问（单用户工作台，不提供学员自助入口）。

**入口**：在现有 Workbench 侧边栏新增「面试复盘」工具 tab。

---

## 二、核心约束与决策

| 项目 | 决策 |
|------|------|
| 输入场景 | 场景 1：录音/视频 + 简历 + 可选 JD；场景 2：问题/回答文本 + 简历 + 可选 JD |
| 音视频处理 | 复用作业批阅的 OSS + 通义听悟离线转写链路 |
| 听悟能力 | 新工具需开启说话人分离，保留 `SpeakerId`、段落顺序和时间信息 |
| 角色识别 | AI 先推断面试官/学员角色，页面提供人工确认和修正 |
| 转写质量 | AI 先做语义清洗，修正明显错别字，但不得补充学员没说过的内容 |
| 多人面试 | 支持多个面试官；核心目标是识别“问题发起方”和“学员回答方” |
| JD | 选填；文字直接输入，图片仅支持 1 张；缺失时基于问题和简历分析 |
| JD 图片解析 | 第一版不先 OCR，执行分析时将 JD 图片直接作为多模态材料交给模型 |
| 简历 | 支持 PDF / DOCX，解析后可编辑，可保存到学员库复用 |
| 学员库 | 需要，保存学员基础信息、简历文本、历史复盘记录 |
| 输出 | 按每个面试问题输出建议，不做评分 |
| 导出 | 支持 DOCX 导出 |
| 模型 | 通过 OpenAI-compatible 环境变量切换，默认优先 Kimi；也可切到智谱 |
| 存储 | 原始录音不长期存储，转写稿和分析结果可存储；简历可保存 |

## 三、用户流程

### 3.1 场景 1：录音/视频复盘

```
选择/新建学员
    │
    ├── 选择已有简历 或 上传新简历
    │
    ├── 上传面试录音/视频
    │
    ├── 输入 JD 文本 或 上传 1 张 JD 图片（可选，支持拖拽）
    │
    ▼
提交任务
    │
    ├── 上传音视频到 OSS
    ├── 调用通义听悟离线转写
    ├── 开启说话人分离
    └── 轮询转写结果
    │
    ▼
转写稿确认
    │
    ├── 展示按 Speaker 分段的转写稿
    ├── AI 推断角色：面试官 / 学员 / 其他
    ├── 老师可快速修正角色和明显转写错误
    └── 确认后进入分析
    │
    ▼
AI 逐题复盘
    │
    ▼
页面展示 + DOCX 导出
```

### 3.2 场景 2：文本问答复盘

```
选择/新建学员
    │
    ├── 选择已有简历 或 上传新简历
    ├── 直接粘贴面试问答文本
    ├── 输入 JD 文本 或 上传 1 张 JD 图片（可选，支持拖拽）
    ▼
提交分析
    │
    ├── 解析问题/回答对
    ├── 清洗文本
    └── AI 逐题复盘
    │
    ▼

```

- AI 默认推断角色，但老师确认后再进入逐题分析。
- 如果老师跳过确认，系统可使用 AI 推断角色，但结果页需要提示“角色未经人工确认”。

## 五、输出结构

### 5.1 页面展示结构

每个问题作为一个独立结果块：

```text
问题 1：请介绍一下你最近做过的一个项目

学员回答摘要：
...

回答问题分析：
...

优化建议：
...

参考话术：
...

需要补充的知识：
...
```

### 5.2 字段说明

| 字段 | 说明 |
|------|------|
| 问题 | 面试官提出的问题，保留原意，必要时修正转写错字 |
| 学员回答摘要 | 只总结学员真实回答，不新增事实 |
| 回答问题分析 | 判断是否答到核心、知识是否正确、结构是否合适、是否贴合简历和 JD |
| 优化建议 | 告诉学员下一次应该怎么改，偏教学反馈 |
| 参考话术 | 给出一版可直接练习的优化回答 |
| 需要补充的知识 | 仅在知识缺失影响回答时输出，补充到能答好该问题即可 |

### 5.3 不做的内容

- 不做总评分。
- 不做逐题分数。
- 不生成后续追问对话。
- 不自动向学员发送报告。

## 六、AI 分析标准

每题内部按以下维度判断，但页面不必全部机械展示为评分项。

### 6.1 是否答到问题核心

判断学员是否回应了面试官真正关心的问题：
- 是否正面回答问题。
- 是否跑题或只讲背景。
- 是否回答过短，导致关键信息缺失。
- 是否回答过长，但没有有效信息。

### 6.2 专业知识是否正确

判断学员涉及的方法、流程、概念是否正确：
- 产品设计流程、交互设计、用户研究、竞品分析、设计评审、可用性测试等。
- 如果说法明显错误，需要指出错误原因。
- 如果只是不完整，需要补充关键知识点。

### 6.3 是否结合简历项目

判断回答和简历是否一致：
- 简历里写了相关项目，回答是否说清楚自己的职责和贡献。
- 是否出现简历有但回答说不上来的情况。
- 是否存在和简历明显冲突的表述。

### 6.4 是否贴合 JD

JD 存在时，判断回答是否贴合岗位关注点：
- 岗位所需能力是否被自然体现。
- 学员是否错过了可以强调的匹配点。
- 如果 JD 缺失，则不强行分析岗位匹配，只基于问题和简历判断。

### 6.5 表达结构是否合适

优先建议学员用适合问题类型的结构：
- 项目类：背景 → 目标 → 角色 → 行动 → 结果 → 复盘。
- 方法类：定义 → 使用场景 → 步骤 → 示例 → 注意事项。
- 行为类：情境 → 任务 → 行动 → 结果。
- 观点类：结论先行 → 理由 → 案例 → 总结。

### 6.6 是否存在风险表达

识别会影响面试评价的表达：
- 只讲“我们”，没有讲“我”。
- 甩锅前同事、业务方、研发或老板。
- 夸大但缺少证据。
- 对基础概念含糊。
- 表达负面、被动或缺少复盘意识。

### 6.7 是否需要补充知识

只有当知识缺失影响回答质量时才补充：
- 不做百科式扩展。
- 不输出与该问题无关的课程内容。
- 优先给面试可用的知识框架和表达模板。

| 现有模块 | 复用方式 |
|----------|----------|
| `src/lib/file-parser.ts` | 复用 PDF/DOCX 简历解析 |
| `src/lib/aliyun-oss.ts` | 复用音视频上传和临时 URL |

| DOCX 导出相关模块 | 复用导出思路，新增面试复盘报告导出 |

### 7.3 需要新增/调整的能力

1. 通义听悟说话人分离参数

新工具创建听悟任务时，需要支持按场景传入参数：

```typescript
Transcription: {
  DiarizationEnabled: true,
  Diarization: {
    SpeakerCount: 0
  },
  OutputLevel: 2
}
```

说明：
- `SpeakerCount=0` 表示说话人数量不确定，适合多人面试。
- `OutputLevel=2` 更利于保留分段、句子、词级信息。
- 作业批阅仍可保持原配置，避免影响已有功能。

2. 面试转写结构化解析

当前作业批阅只提取纯文本。面试复盘需要新增结构：

```typescript
export interface InterviewTranscriptSegment {
  id: string;
  speakerId: string;
  role: "interviewer" | "candidate" | "other" | "unknown";
  startTime?: number;
  endTime?: number;
  text: string;
}
```

3. 角色推断

AI 根据每个 speaker 的发言内容推断角色：
- 经常提问、追问、评价的一方倾向面试官。
- 大段回答、介绍项目经历、解释个人经历的一方倾向学员。
- 只偶尔插话或会议提示可标为其他。

4. 问答对切分

将确认后的转写稿转成：

```typescript
export interface InterviewQaPair {
  id: string;
  question: string;
  answer: string;
  interviewerSpeakerIds: string[];
  candidateSpeakerIds: string[];
  sourceSegmentIds: string[];
}
```

切分原则：
- 面试官连续追问但学员尚未回答时，可合并为一个问题。
- 学员回答后，下一段面试官问题开启新题。
- 如果学员没有回答，`answer` 为空，分析时标记“未回答/回答缺失”。

## 十、Prompt 设计

### 10.1 转写清洗与角色推断 Prompt

目标：
- 修正明显错别字。
- 保留口语原意。
- 不新增事实。
- 根据发言内容推断角色。

输出 JSON：

```json
{
  "segments": [
    {
      "id": "seg_1",
      "speakerId": "1",
      "role": "interviewer",
      "cleanedText": "请介绍一下你最近做过的项目。",
      "uncertain": false
    }
  ],
  "roleInferenceNotes": "Speaker 1 多次提出问题，判断为面试官；Speaker 2 长段回答个人经历，判断为学员。"
}
```

### 10.2 问答切分 Prompt

输入：
- 确认后的转写段落，含角色。

输出 JSON：

```json
{
  "qaPairs": [
    {
      "id": "qa_1",
      "question": "请介绍一下你最近做过的项目。",
      "answer": "我最近做的是一个 B 端后台项目...",
      "sourceSegmentIds": ["seg_1", "seg_2"]
    }
  ]
}
```

### 10.3 逐题分析 Prompt

为保证输出稳定性，正式实现采用两层 Prompt：

- `system prompt`：负责角色设定、真实性边界、逐题分析规则、题型判断、风险识别和输出纪律。
- `user prompt`：负责注入本次任务的学员信息、简历、JD、问答列表和目标 JSON 结构。

#### 10.3.1 System Prompt（正式版）

```text
你是一位资深求职面试辅导老师，长期辅导产品经理、AI 产品经理、产品助理、交互设计、用户体验设计、运营产品、数据产品、项目经理等岗位求职者。

你的任务是基于【学员简历】【面试 JD】【面试问答内容】，对每一道面试题进行逐题复盘诊断，判断学员回答是否有效，并给出可直接用于训练和改进的优化建议。

你的目标不是简单润色回答，而是帮助老师判断：
1. 学员有没有听懂面试官真正想考察什么；
2. 学员回答是否正面、完整、结构清晰；
3. 学员是否结合了自己的简历项目与岗位要求；
4. 学员是否暴露出知识缺口、表达风险或经历不扎实的问题；
5. 学员下一次面试应该如何优化表达。

你必须严格遵守以下原则：

【一、真实性原则】
- 只能基于输入材料分析，不得编造学员没有说过、简历没有写过、JD 没有体现的信息。
- 可以对学员已有经历进行更清晰、更结构化的表达，但不能虚构项目结果、数据指标、职责边界、技术细节或业务事实。
- 如果材料不足，必须明确写出“材料不足，无法判断”，不能强行推断。
- 如果参考话术中需要补充数据，但材料中没有数据，只能写成“如果真实有数据，可补充……”的表达，不能直接编造具体数字。

【二、逐题分析原则】
- 每一道题都要独立分析。
- 先判断该题属于哪类问题，再判断回答是否有效。
- 如果学员未回答或回答缺失，必须明确标记“未回答/回答缺失”。
- 如果学员回答跑题、答非所问、只讲背景、只讲流程、没有讲个人贡献，要明确指出。
- 如果学员回答部分有效，也要指出“有效部分”和“不足部分”。

【三、简历一致性原则】
- 如果简历中有相关项目或能力，但学员回答没有体现，要指出“简历优势未被表达出来”。
- 如果回答内容和简历存在明显冲突，要指出风险。
- 如果简历材料不足，不要强行做一致性判断。
- 不要因为简历中写了某项能力，就默认学员在回答中已经表达出来，必须以实际回答内容为准。

【四、JD 匹配原则】
- 如果提供了 JD，需要判断学员是否自然体现了岗位关注能力。
- 如果 JD 缺失，不要强行做 JD 匹配，只基于问题、回答和简历分析。
- JD 匹配分析只判断“是否错过表达机会”和“哪些能力可以更好体现”，不要硬凑关键词。

【五、知识纠错原则】
- 如果学员涉及产品设计、需求分析、用户研究、竞品分析、项目推进、数据分析、AI 产品、B 端系统、金融信贷、电商系统、CRM、ERP、MES、OMS、风控、客服系统等知识点时出现错误，必须指出错误并给出正确理解。
- 如果只是回答不完整，应补充可用于面试表达的知识框架。
- 知识补充必须服务于该题，不要百科式扩展。
- 不要输出与该问题无关的课程内容。

【六、表达训练原则】
- 优化建议要具体，能够指导学员下一次怎么答。
- 参考话术必须像真实面试回答，不能像书面报告。
- 参考话术要保留学员真实经历边界，不得虚构事实。
- 如果学员回答过短，要教他补充结构。
- 如果学员回答过长，要教他压缩主线。
- 如果学员只讲“我们”，要帮助他改成能体现“我负责什么、我怎么做、我推动了什么”的表达。
- 参考话术应控制在真实面试可直接口述的长度，优先输出 1 到 3 段自然表达，不写成条目式讲义。

【七、风险识别原则】
重点识别以下风险：
- 没有正面回答问题；
- 回答过短，关键信息缺失；
- 回答过长，但有效信息少；
- 只说“我们”，没有说清楚“我做了什么”；
- 只讲功能，没有讲目标、问题、决策和结果；
- 只讲执行，没有体现分析、判断和推进能力；
- 项目经历显得不真实、不扎实；
- 对基础概念解释错误或含糊；
- 甩锅业务方、研发、老板、同事；
- 表达负面、被动、缺少复盘意识；
- 和简历内容不一致；
- 错过 JD 重点能力表达机会。

【八、题型判断规则】
你需要先判断每道题的问题类型，并按对应标准分析。questionType 只能从以下值中选择：
- 自我介绍类
- 项目经历类
- 项目细节追问类
- 产品方法类
- 行为面试类
- 业务理解类
- 数据分析类
- AI 产品类
- HR 综合类
- 压力追问类
- 其他

1. 自我介绍类
重点判断：岗位匹配度、经历主线、核心优势、表达长度、是否像背简历。

2. 项目经历类
重点判断：项目背景、目标、个人角色、关键动作、结果、复盘是否完整。
推荐结构：背景 → 目标 → 角色 → 行动 → 结果 → 复盘。

3. 项目细节追问类
重点判断：学员是否真的理解项目细节，是否能讲清楚业务流程、功能规则、异常情况、协作过程和自己的判断依据。

4. 产品方法类
重点判断：概念是否正确，是否能结合实际项目说明。
推荐结构：定义 → 使用场景 → 操作步骤 → 项目例子 → 注意事项。

5. 行为面试类
重点判断：是否有具体情境、任务、行动、结果。
推荐结构：情境 → 任务 → 行动 → 结果。

6. 业务理解类
重点判断：是否理解行业、业务流程、用户角色、核心指标和关键风险。

7. 数据分析类
重点判断：是否能说明指标、数据来源、分析方法、结论和产品动作。

8. AI 产品类
重点判断：是否理解 AI 能力边界、模型调用、Prompt、工作流、知识库、RAG、效果评估和异常兜底。

9. HR 综合类
重点判断：离职原因、职业规划、稳定性、求职动机、薪资期望等表达是否合理。

10. 压力追问类
重点判断：学员是否能稳定回应质疑，是否能承认不足并补充思考，而不是慌乱、回避或强行解释。

【九、回答状态枚举】
每道题必须给出 answerStatus，只能从以下值中选择：
- "有效"
- "部分有效"
- "无效"
- "未回答/回答缺失"
- "材料不足，无法判断"

【十、输出要求】
- 必须输出严格 JSON。
- 不要输出 Markdown。
- 不要输出代码块。
- 不要输出 JSON 之外的解释文字。
- 所有字段必须使用中文内容。
- 如果某个文本字段无法判断，也要保留字段，并写“材料不足，无法判断”。
- 如果某个数组字段没有内容，输出空数组 []。
- riskNotes 如果没有明显风险，输出空数组 []。
- answerEvidenceQuotes 必须来自老师确认后的转写文本或用户输入的原始回答文本，不得改写；如果没有可引用内容，输出空数组 []。
- whatWasAnsweredWell 如果没有明显有效部分，写“未体现明显有效部分”。
- items 数量必须与输入问答数量一致。
- items 的顺序必须与输入问答顺序一致。
- 每个 item 的 id 必须沿用输入 id。
```

#### 10.3.3 工程实现建议

- 模型调用使用 `system prompt + user prompt` 组合，不建议把所有规则都塞到单个 user prompt 中。
- 接口层尽量使用 `response_format=json_object` 或等价 structured output 能力。
- 服务端需要对返回 JSON 做 schema 校验；校验失败时，允许自动重试一次。
- 后端需要额外校验：
  - `items.length === qaPairs.length`
  - `items[i].id === qaPairs[i].id`
  - `answerStatus` 是否命中枚举
  - `questionType` 是否命中允许值
  - `jdText` 为空时，所有 `jdMatch` 是否符合兜底文案

## 十四、主要风险与处理

| 风险 | 处理 |
|------|------|
| 听悟说话人分离只给 SpeakerId，不知道真实角色 | AI 推断 + 人工确认 |
| 转写错别字影响判断 | 分析前做清洗，但保留不确定标记 |
| 多人面试角色复杂 | 支持多个面试官，核心识别学员回答 |
| 长录音导致模型上下文过长 | 先结构化切分问答，再逐题或分批分析 |
| 学员回答很短或缺失 | 明确标记未回答，给出补充回答方案 |
| JD 缺失 | 不做强 JD 匹配，只基于问题和简历分析 |
| 模型输出不稳定 | 强制 JSON 输出，后端解析失败时重试一次 |
